# Phase 4a Round 2 — Provenance Check (item 1)

**Question:** did round 1's tests use the original stored `scr_scores` rows, or
rows regenerated by the materialized pipeline after the bug fixes (the
`scr_anchors_asof` revenue-anchor gap, the exact-vs-nearest-period matching
bug, the out-of-order-filing `pe0_prior` bug)?

**Answer: the original stored `scr_scores` rows, for all 5 profile_versions.**

rows are already confirmed bit-for-bit identical to what the canonical

## Why `a_v1_hist`/`a_v1_hist_rd`/`b_v1` were not re-diffed from scratch this round

Their 0-diff equivalence checks are recorded immutably in `scr_job_runs`
(ids 5/6/7) against the *current* committed materialized pipeline — the
same scripts, same commit hash, still on disk unchanged — and neither the
upstream `scr_fundamentals`/`scr_period_facts`/`scr_anchors_asof` tables nor
the stored `scr_scores` rows have been written to since. Re-running an
already-bit-identical 77k-166k row diff a second time against unchanged
inputs would reproduce the same 0 with no new information, at a real time
cost (160-195s each, 3x). `a_v1_hist_qqq_gate` and `a_v1_hist_ff12` **were**
re-run fresh because (a) `a_v1_hist_ff12` was never checked in round 1 at
all, and (b) it's cheap enough (~10s each) that re-confirming cost nothing.

## Conclusion for round 2

Since every profile_version's stored `scr_scores` rows are confirmed
identical to the canonical (bug-fixed) generator's output, **no row
regeneration via `scr_scores_corrections` is required.** All tests below use
the existing stored `scr_scores` rows directly, with full confidence that
doing so is equivalent to using freshly-regenerated-and-corrected rows.
